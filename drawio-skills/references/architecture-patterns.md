# 架构图模式库（专业骨架）

这几套骨架是从"什么样的架构图算画得好"里抽象出来的固定结构。**先选模式，再填内容**——不要从空白画布开始画。

配合 `build_diagram.py` 使用：每个模式给出 layer / group / role 的填法，直接落成 JSON spec。

---

## 模式一：分层架构（最常用）

**适用**：技术架构图、系统分层图、微服务总览。
**视觉**：纵向 3~5 层，每层一个泳道（分组描边色区分），层间箭头向下，同层节点横向排开。

```
layer 0  接入层      [Web] [App] [Admin]        ← blue 分组
layer 1  网关层      [API Gateway]              ← blue 分组
layer 2  业务层      [认证] [订单] [支付]        ← green 分组
layer 3  数据层      [Kafka] [MySQL] [Redis]    ← red 分组
```

填写要点：
- 每层一个 group，`color` 按 接入=blue / 业务=green / 数据=red / 外部=default。
- 网关 role=`gateway`，存储 role=`database`，队列 role=`queue`。
- 外部依赖（第三方支付、短信）单独放一个 group，`dashed:true`。
- 边只画相邻层，不要跨层直连（跨层会穿模）；确需跨层时拆成两段。

参考实例：`examples/ecommerce-architecture.json`。

---

## 模式二：C4 Container（系统容器图）

**适用**：给非技术干系人看的系统全景，强调"谁用什么技术、和谁交互"。
**视觉**：4 类容器 + 外部用户，颜色严格对应 C4 语义。

| C4 元素 | role | 说明 |
|---------|------|------|
| 用户 / 外部系统 | `external` + `dashed:true` | 系统边界外 |
| Web/SPA 容器 | `service` | 前端 |
| API 应用容器 | `service` | 后端服务 |
| 数据库容器 | `database` | 持久化 |
| 消息队列 | `queue` | 异步 |

填写要点：
- 用 group 画出"系统边界"大框（color=default），把自有容器框进去。
- 每条边必须带 label，写清协议或用途（HTTPS / JDBC / REST / 事件）。
- 容器 label 格式建议「名称 [技术]」，如「订单服务 [Spring Boot]」。

---

## 模式三：数据链路 / ETL

**适用**：数据中台、日志管道、实时计算链路。
**视觉**：`direction=LR`，从左（数据源）到右（消费端）单向流动。

```
[业务库] [埋点]  →  [Kafka]  →  [Flink]  →  [ClickHouse]  →  [BI 看板]
  database        queue       service      database        service
```

填写要点：
- `direction: "LR"`，layer 沿数据流向递增。
- 每条边 label 写明数据形态（binlog / JSON 事件 / 聚合结果）。
- 异步环节 kind=`async`（虚线），与同步调用区分。
- 存储节点统一 `database`，不要混用 service。

---

## 模式四：安全域 / 网络拓扑

**适用**：等保、政务外网、钓鱼防护、零信任架构。
**视觉**：按信任级别横向切分区域，区域间用虚线边 + 明确管控点。

| 区域 | group color | 内容 |
|------|-------------|------|
| 互联网区 | `red` | 外部用户、攻击者 |
| DMZ 区 | `blue` | WAF、负载均衡、反向代理 |
| 应用区 | `green` | 业务服务、认证 |
| 数据区 | `darkred` | 数据库、备份 |

填写要点：
- 每个安全域一个 group，用 `color` 编码信任级别（越核心越深）。
- 跨域边必须画在管控点上（防火墙 / 网关 / 认证），不要直接连两端的节点。
- 认证、鉴权节点 role=`security`。
- 高风险标注用 role=`error`。

---

## 模式五：调用链 / 时序（简化）

**适用**：单次请求经过了哪些组件、哪里可能失败。
**视觉**：`direction=LR` 的横向链路 + 失败分支。

填写要点：
- 主链路从左到右，layer 递增。
- 错误/降级路径用 role=`error` 的节点 + kind=`async` 的边。
- 每个节点 label 尽量带耗时或 SLA（如「订单服务 (p99 200ms)」）。

> 严格时序图（带生命线和消息编号）建议用 Mermaid `sequenceDiagram` 转换，本 DSL 不擅长表达时序语义。

---

## 通用质量规则（所有模式都适用）

1. **层数控制**：3~5 层最佳。超过 6 层考虑拆图或合并。
2. **每层节点数**：不超过 7 个（人眼短期记忆上限）。超过就分组或拆图。
3. **边不跨层**：跨层边会穿过中间节点。真需要时拆成两段，或改用注释说明。
4. **颜色即语义**：不要为了好看随意换色。role 决定颜色，看图人靠颜色快速定位。
5. **每个节点都要有边**：孤立节点要么是噪声，要么该单独说明它为什么在图上。
6. **标签短**：节点 label 控制在 8 个字以内；长说明放到边 label 或文档，不要塞进节点。
7. **先 lint 后交付**：生成后必须跑 `validate.py`，ERROR 清零。

## 如何从需求选模式

| 用户说 | 选哪个模式 |
|--------|-----------|
| "画个技术架构图 / 系统架构" | 模式一 分层架构 |
| "C4 / 容器图 / 给领导看的系统全景" | 模式二 C4 |
| "数据链路 / 日志管道 / 实时计算" | 模式三 数据链路 |
| "网络拓扑 / 等保 / 安全域 / 政务外网" | 模式四 安全域 |
| "请求流程 / 调用链 / 哪里会失败" | 模式五 调用链 |
| "思维导图 / 标准流程图 / 甘特图" | 不走本模式库，用官方 Mermaid 转换路径 |
